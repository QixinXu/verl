# 反思

本次交付只做了 rollout，没有做梯度更新：验证了 harness 是对的（数据通路、功劳计算、reward 回填、分组 advantage、库的生命周期），但方法能不能真的让模型变好，没有实验证据。下文的数字来自脚本策略的 rollout（手写规则代替模型，每条 skill 的真实价值事先知道，见 VALIDATION §3），说明问题存在，不代表真模型上的大小。

## 1. 主要缺点

**1. 重复写一条库里已有的 skill，也能拿到正功劳。**

举个例子：库里已经有一条"怎么加热东西"的 skill X，模型又写了一条内容一样的 X'。X' 没带来任何新东西，功劳本该是 0，实际算出来是正的。原因是功劳公式两边比的不是同一类轨迹：实验组只统计"加载了 X' 并照着做"的轨迹，这些轨迹做得好；对照组的基线是全部轨迹的平均，里面有没加载 X 的、加载了没照着做的，基线被拉低了。

脚本策略上，真正有用的新 skill 平均功劳 +0.050（83% 为正），重复的 skill 是 +0.031（76% 为正），差得不多。重复的 skill 会被入库时的去重挡在库外，但写它的 token 已经拿到了奖励。修法是对照组也只统计加载并照着做了库里 skill 的轨迹；离线算过，重复 skill 的功劳降到 +0.003，有用 skill 仍有 +0.042。

**2. 使用权重是一个近似。** 影响力衡量的是"同样的动作，没有 skill 正文时概率低多少"，测不到"没有正文时会走出完全不同的轨迹"。它还按加载之后的整段轨迹平均，失败的轨迹更长，后面和 skill 无关的动作把影响力稀释了，所以失败被打折扣：脚本策略上使用权重和得分正相关（+0.35 到 +0.73）。改法是只算加载之后固定的前几步，或者对少量轨迹从加载点重新采样做真正的反事实来校准。

**3. 冷启动：模型不加载，就没有信号。** 功劳只来自加载了新 skill 的轨迹。未微调的 Qwen3.5-4B 会主动写（各步 25%–91% 的 A 轨迹写了 skill），但很少加载（检验题上 1%–16%），所以大多数新 skill 的功劳是 0，写 skill 的训练信号很稀。实际训练前需要先用 SFT 教会两个动作的格式和时机，这一步没有做。

**4. 只奖励短期、同题型的价值。** 写 skill 的 reward 只看当步、同题型的检验题。跨很多步、跨题型才体现的价值不进训练信号，只影响 skill 在库里留多久。检验题按 benchmark 自带的题型标签选，没有现成题型的场景要先给题目分类。

## 2. Scale

| 瓶颈 | 量级 |
|---|---|
| 检验要额外跑轨迹 | 默认配置下一个训练单元约 48 条轨迹（4 个候选时），是只做 A 的 6 倍。对照组和实验组的轨迹也参与训练，不全是浪费；但公平的 baseline 应该是同样轨迹预算的 GRPO |
| 单元内有依赖 | 检验要等 A 做完、skill 写出来，一个单元的延迟约为两局；sync 模式下一步的时间由最慢的单元决定 |
| 库在步末提交 | 库的版本绑定在 sync trainer 的 step 上，不能直接用异步 trainer。改法是库加版本号，每个单元开始时钉住一个版本 |
| 环境 | TextWorld 每个进程只能跑一个环境线程，并行度靠 worker 进程数 |

计算量随候选数线性增长，没有随库大小增长的部分（检索只取 N 条），库变大后只需要把全量相似度换成向量索引。

## 3. 最值得做的改进

1. **修掉缺点 1**：对照组只统计用了库里 skill 的轨迹。
2. **降低功劳的噪声而不加算力**：对照组和实验组用相同的随机种子；库里 skill 的效用用历次测量的累计值而不是最近一次。
3. **SFT 预热 + 真正跑训练**：报同一 checkpoint 带库、不带库、打乱的库三个数，以及留出题型上的迁移。

# 对这道题本身的反思

## 题目的实效性

**1. 题目对 verl 的描述已经过时了一半。** 题面说"verl 的 rollout 是无状态、单轮一次性的"。当前 verl（V1 trainer）已经有 AgentLoop、多轮对话、工具调用、一个 session 多条输出、TransferQueue、可替换的 AgentLoopManager 和 ReplayBuffer。"单轮"不再成立，多轮本身不需要改造。仍然成立、也是真正要改的是三条更细的假设：**轨迹之间没有共享状态；同一 prompt 的 n 个 session 相互独立；一个 session 只有一个 reward、按 uid 比较**。所以工程难点已经从"让 verl 支持多轮有状态交互"转移到"共享可变状态在分布式 rollout 下的一致性语义"和"异构 credit"。题面如果更新成后者，考察的东西会更准。

**2. 这个方向在一年内被做了很多遍。** 调研到的 2025 年底到 2026 年的工作里，SAGE、SkillRL、Skill1、SkillMaster、SkillOS、D2Skill、Connect-the-Dots 等都在做"RL 训练中带 skill 库"，其中好几篇正是在 verl 系框架、ALFWorld、Qwen 小模型上做的，连"当步反事实检验 + 分角色 advantage"都已有人做过（SkillMaster）。所以题目强调"不要求创新、要求讲清楚为什么这么设计"是对的；但也意味着"做出一个能跑的闭环"的区分度在下降，区分度在于**能不能说清楚自己的 reward 在什么假设下是对的、在哪里会坏**。

**3. 题目没有问的那个问题才是最要紧的：skill 在 RL 训练里到底图什么。** 调研里多篇工作报告：训练完以后把 skill 去掉，掉点很小——RL 会把 skill 吸收进权重。那么"在训练中进化一个库"至少有三种不同的目的，对应不同的设计和评测：

| 目的 | 库的角色 | 该怎么评 |
|---|---|---|
| 加速训练 | 探索的脚手架，训练完可以扔 | 同算力下达到同样成功率的步数；最后去掉库不掉点才是成功 |
| 训练"写 skill / 用 skill"这个元能力 | 训练时的库不重要，重要的是部署时权重冻结、库继续长 | 冻结权重，在留出域上从空库开始，看成功率随经验的增长曲线 |
| 承载不该进权重的知识 | 环境特有、会变化的事实 | 环境规则中途改变后的恢复速度 |

题目把这三者混在"自我进化的闭环"一个词里。这里的实现隐含地偏向第二种（写和选都是被训练的动作，评测留出了两个题型），但题目没要求任何能区分这三者的验证。

## 可以改进、也更有意思的方向

**(a) 换一个 skill 不可被内化的环境。** ALFWorld 的知识是固定的，7B 模型已接近天花板，skill 最终都会被权重吸收。更适合考察 skill 的是**隐藏规则因环境实例而变**的任务：规则每个 world 不同，权重学不到具体规则，只能学"如何发现规则并写下来"。这正是 meta-RL 的设定（比如程序化生成隐藏规则的 Symbolic Alchemy 这类环境，或者"同一个代码仓库里的连续任务"，skill 就是仓库的约定）。在这种设定下，库按环境实例重置、writer 跨环境训练，非平稳和内化两个问题同时消失，reward 归因也自然是"这个环境里后续任务的提升"。

**(b) 把题目从"实现闭环"改成"设计一致性模型"。** 给定 verl 的异步 trainer（轨迹跨权重版本、有 staleness 丢弃），问：库作为第二份可变状态，应该提供什么隔离级别？快照隔离、按 uid 钉版本、提交的原子性、与权重版本的关系、checkpoint 恢复时库和 in-flight 轨迹怎么对齐。这是纯 harness 问题，有明确的对错，现在的题面基本没碰到。

**(c) 写哪里的决策。** skill 库、情景记忆、权重是三种存储。"这条经验该写进哪一种"本身可以是学出来的：可复用的流程进 skill，一次性的事实进记忆，高频到不值得检索的进权重（内化）。现在的题目只考察第一种。
